2. Granularity: 10 major muscle groups — chest, back, shoulders,

5. Coloring: single accent hue (#e94560, the app's existing --accent

   volume — NOT a different color per muscle group.

You also asked about sourcing exercise-to-muscle data from an open
GitHub dataset (e.g. free-exercise-db). We did NOT go that route —
tagging is fully manual via dropdown (decision #3 above). That
remains an option later if you want auto-suggestion instead of
always picking manually.

You also clarified Part 5's "daily reset": it is NOT a delete-based
reset. Each workout already has a `date` column — Monday's workout
and Wednesday's workout both stay in the database as their own
dated rows. "Analytics" means querying/comparing across those dated
rows (e.g. total volume Monday vs Wednesday), not wiping and
rebuilding data daily. Nothing was built for this yet — it's queued
for Part 5.

------------------------------------------------------------------
3. CORRECTIONS FOUND DURING INVESTIGATION
------------------------------------------------------------------
These are things that turned out different from the original
assumption once the actual code was read — important to know so you
don't get confused later.

CORRECTION 1 — There is only ONE live database, not two.
  Original assumption: server/db.js (SQLite/better-sqlite3) = local
  dev database, server/db-pg.js (Postgres/Neon) = production
  database — a typical dev/prod split.
  Actual reality: server/index.js and EVERY route file
  (auth.js, workouts.js, exercises.js, sets.js, prs.js,
  r-achievements.js) require server/db-pg.js only. server/db.js is
  never required by the running server at all. The only two files
  that touch db.js are server/check-ach.js and server/checkpr.js —
  standalone debug scripts not wired into index.js.
  Practical effect: your local dev server and your production
  deployment both talk to the SAME Neon Postgres database (via
  DATABASE_URL in server/.env). There is no separate local SQLite
  database actually in use. server/db.js was still updated for
  consistency/hygiene, but it is not on the critical path.

CORRECTION 2 — Express route-ordering hazard.
  server/routes/workouts.js already had `router.get('/:id', ...)`
  registered BEFORE `router.get('/progress/:exerciseName', ...)`.
  This was only safe because "/progress/xxx" has two path segments,
  so Express's `/:id` pattern (one segment) doesn't match it.
  A new single-segment route like "/muscle-volume" WOULD have
  collided with `/:id` if placed after it — Express would treat the
  literal string "muscle-volume" as the id parameter and run
  `SELECT * FROM workouts WHERE id = 'muscle-volume'`, which is a
  broken/meaningless query, not a 404.
  Fix applied: the new `/muscle-volume` route is registered BEFORE
  `/:id` in workouts.js. Confirmed by directly reading the file.

CORRECTION 3 (minor, not fixed, just flagged) — checkpr.js is
  misleadingly named. Despite the name, its contents are byte-for-
  byte identical to check-ach.js: it just logs the achievements
  table from the (unused) db.js. It does NOT contain PR-checking
  logic — real PR logic lives in server/routes/sets.js. This is
  pre-existing tech debt, left untouched, just documented here so
  you're not misled by the filename later.

FILE: server/setup-db.js  (EDITED — the schema that actually matters)
--------------------------------------------------------------
WHY: This is the one-time script that creates tables in the live
Neon Postgres database. Since `CREATE TABLE IF NOT EXISTS` does
nothing to an already-existing table, a plain column addition to
the CREATE statement would NOT have patched the live table. The
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` line is what actually
does the work, and it's safe to leave permanently — reruns are
no-ops once the column exists.
ACTION STILL NEEDED FROM YOU: run `node setup-db.js` from the
`server/` folder to apply this to your live database. This was
deliberately NOT run automatically — it mutates your production
database, and that's your call to make, not an automatic step.

Column design: plain `TEXT`, nullable, no database-level CHECK
constraint. The 10-value whitelist is enforced at the application
layer (in the route handler) instead, because there's a single
write path (your own API) and a single user — a lookup table or DB
constraint would be over-engineering for this. Nullable so existing
untagged exercises aren't given a fabricated value.

FULL FILE:
```javascript
// one-time script: creates all tables in the Neon Postgres database
// run with: node setup-db.js
require('dotenv').config()
const pool = require('./db-pg');

async function setup() {
  // Postgres runs multiple statements in one query() call
  await pool.query(`
   CREATE TABLE IF NOT EXISTS users (
      id SERIAL PRIMARY KEY,
      username TEXT NOT NULL UNIQUE,
      password_hash TEXT NOT NULL,
      created_at TIMESTAMP DEFAULT NOW()
    );

    CREATE TABLE IF NOT EXISTS workouts (
      id SERIAL PRIMARY KEY,
      user_id INTEGER NOT NULL,
      name TEXT NOT NULL,
      date TIMESTAMP DEFAULT NOW(),
      FOREIGN KEY (user_id) REFERENCES users(id)
    );

    CREATE TABLE IF NOT EXISTS exercises (
      id SERIAL PRIMARY KEY,
      workout_id INTEGER NOT NULL,
      name TEXT NOT NULL,
      muscle_group TEXT,
      FOREIGN KEY (workout_id) REFERENCES workouts(id)
    );

    -- CREATE TABLE IF NOT EXISTS is a no-op against the already-existing prod table,
    -- so this ALTER is what actually adds the column there. Safe to rerun.
    ALTER TABLE exercises ADD COLUMN IF NOT EXISTS muscle_group TEXT;

    CREATE TABLE IF NOT EXISTS sets (
      id SERIAL PRIMARY KEY,
      exercise_id INTEGER NOT NULL,
      reps INTEGER NOT NULL,
      weight REAL NOT NULL,
      set_number INTEGER NOT NULL,
      FOREIGN KEY (exercise_id) REFERENCES exercises(id)
    );

    CREATE TABLE IF NOT EXISTS prs (
      id SERIAL PRIMARY KEY,
      user_id INTEGER NOT NULL,
      exercise_name TEXT NOT NULL,
      weight REAL NOT NULL,
      reps INTEGER NOT NULL,
      set_id INTEGER NOT NULL,
      achieved_at TIMESTAMP DEFAULT NOW(),
      FOREIGN KEY (user_id) REFERENCES users(id),
      FOREIGN KEY (set_id) REFERENCES sets(id)
    );

    CREATE TABLE IF NOT EXISTS achievements (
      id SERIAL PRIMARY KEY,
      user_id INTEGER NOT NULL,
      exercise_name TEXT NOT NULL,
      tier INTEGER NOT NULL,
      unlocked_at TIMESTAMP DEFAULT NOW(),
      FOREIGN KEY (user_id) REFERENCES users(id),
      UNIQUE (user_id, exercise_name, tier)
    );
  `)

  console.log(' Tables created succesfully')
  await pool.end()            // close the pool so the script exits cleanly
}

setup().catch((err) => {
  console.error('Setup failed: ', err)
  pool.end()
})
```

FULL FILE:
```javascript
const express = require('express')
const router = express.Router()
const pool = require('../db-pg')
const requireAuth = require('../middleware/auth')
const { MUSCLE_GROUPS } = require('../constants/muscleGroups')

// POST /api/workouts/:workoutId/exercises
// adds a new exercise to a specific workout
// notice the route is just '/:workoutId/exercises' here because in index.js
// this router will be mounted at '/api/workouts' — so the full path combines
router.post('/:workoutId/exercises', requireAuth, async(req, res) => {

  // workoutId - workout added to, name - exercise name, muscle_group - tag used by the anatomy chart
  const { workoutId } = req.params
  const { name, muscle_group } = req.body

  if (!name) return res.status(400).json({ error: 'All fields required' })
  if (!muscle_group || !MUSCLE_GROUPS.includes(muscle_group)) {
    return res.status(400).json({ error: 'Invalid muscle_group' })
  }

  // verify the workout exists AND belongs to this user before adding to it
  // this is the authorization check — you can't add exercises to someone else's workout
  const workoutResult = await pool.query('SELECT * FROM workouts WHERE id = $1', [workoutId])
  const workout = workoutResult.rows[0]

  if (!workout) return res.status(404).json({ error: 'Workout not found' })
  if (workout.user_id !== req.userId) return res.status(403).json({ error: 'Forbidden' })

  try {
    // insert the exercise
    // foreign key in action: exercises.workout_id = workouts.id
    const result = await pool.query(
      'INSERT INTO exercises (workout_id, name, muscle_group) VALUES ($1, $2, $3) RETURNING id, name, muscle_group',
      [workoutId, name, muscle_group]
    )

    // fetch and return the newly created exercise
    const newExercise = result.rows[0]

    // return
    res.status(201).json(newExercise)
  } catch {
    res.status(500).json({ error: 'Failed to create exercise' })
  }
})

// DELETE /api/exercises/:id
router.delete('/exercises/:id', requireAuth, async (req, res) => {
  const { id } = req.params

  // verify if the exercise exists
  const exerciseResult = await pool.query('SELECT * FROM exercises WHERE id = $1', [id])
  const exercise = exerciseResult.rows[0]
  if (!exercise) return res.status(404).json({ error: 'Exercise not found' })

  // exercises don't directly have user_id — we have to climb up to workouts
  // this is the chain in practice: exercises → workouts → user_id
  const workoutResult = await pool.query('SELECT * FROM workouts WHERE id = $1', [exercise.workout_id])
  const workout = workoutResult.rows[0]
  if (!workout) return res.status(404).json({ error: 'Workout not found' })
  if (workout.user_id !== req.userId) return res.status(403).json({ error: 'Forbidden' })

  // delete PRs for all sets belonging to this exercise, BEFORE deleting the sets
  await pool.query(`
    DELETE FROM prs
    WHERE set_id IN (
      SELECT id FROM sets WHERE exercise_id = $1
    )
  `, [id])

  // delete child sets first — foreign key constraint prevents deleting
  // an exercise while sets still reference it via exercise_id
  await pool.query('DELETE FROM sets WHERE exercise_id = $1', [id])

  // now safe to delete the exercise itself
  await pool.query('DELETE FROM exercises WHERE id = $1', [id])
  res.json({ message: 'Exercise deleted' })
})

module.exports = router
```

```javascript
const express = require('express')
const router = express.Router()
const pool = require('../db-pg')
const requireAuth = require('../middleware/auth')

// helper — transforms flat JOIN rows into nested exercise objects with sets arrays
function groupExercisesWithSets(rows) {

  // reduce() transforms an array into a single accumulated value
  // here we're accumulating an object where each key is an exercise id
  const map = rows.reduce((acc, row) => {

    // if we haven't seen this exercise id before, make one
    if (!acc[row.exercise_id]) {
      acc[row.exercise_id] = {
        id: row.exercise_id,
        name: row.exercise_name,
        muscle_group: row.muscle_group,
        sets: []
      }
    }


    // if this row has a set (LEFT JOIN means set columns could be null)
    // push the set into this exercise's sets array
    if (row.set_id) {
      acc[row.exercise_id].sets.push({
        id: row.set_id,
        reps: row.reps,
        weight: row.weight,
        set_number: row.set_number
      })
    }
    return acc
  }, {})

  // convert the object of exercises into an array
  return Object.values(map)
}

// GET all workouts for the logged-in user
// requireAuth runs first — attaches req.userId if token is valid
router.get('/', requireAuth, async (req, res) => {
  const result = await pool.query(
    'SELECT * FROM workouts WHERE user_id = $1 ORDER BY date DESC',
    [req.userId]
  )
  // the whole array
  res.json(result.rows)
})


// POST /
router.post('/', requireAuth, async (req, res) => {
  // destructure name from req.body
  const { name } = req.body;

  // validate if name exists
  if (!name) {
    return res.status(401).json({ error: 'Name not found!' });
  }

  // insert the workout — user_id comes from req.userId set by requireAuth
  // this is how every workout gets tied to its owner
  try {
    const result = await pool.query(
      'INSERT INTO workouts (user_id, name) VALUES ($1, $2) RETURNING id',
      [req.userId, name]
    )// ↑ user   ↑ workout name

    // after inserting, fetch the new workout and return it (postgres format)
    const newWorkout = result.rows[0]

    // return, 201 = Created
    res.status(201).json(newWorkout)

  } catch (err){
    console.error(err)
    return res.status(500).json({ error: 'Failed to create workout'});
  }
})

// GET /api/workouts/muscle-volume
// total tonnage (reps x weight) per muscle group, across ALL of the user's workouts.
// registered BEFORE /:id — a single-segment path here would otherwise be
// swallowed by the /:id route above and treated as an (invalid) workout id
router.get('/muscle-volume', requireAuth, async (req, res) => {
  const result = await pool.query(`
    SELECT exercises.muscle_group, SUM(sets.reps * sets.weight) AS tonnage
    FROM sets
    JOIN exercises ON sets.exercise_id = exercises.id
    JOIN workouts ON exercises.workout_id = workouts.id
    WHERE workouts.user_id = $1 AND exercises.muscle_group IS NOT NULL
    GROUP BY exercises.muscle_group
  `, [req.userId])

  res.json(result.rows)
})

// GET/:id - one workout with all its exercises and sets
router.get('/:id', requireAuth, async (req, res) => {
  // req.body is for POST/PATCH
  const { id } = req.params;

  // verify if workout exists
  const workoutResult = await pool.query('SELECT * FROM workouts WHERE id = $1', [id])
  const workout = workoutResult.rows[0]
  if (!workout) return res.status(404).json({ error: 'Workout not found' })

  // then verify if it belongs to the logged in user
  if (workout.user_id !== req.userId) return res.status(403).json({ error: 'Forbidden' })

  // JOIN query — pulls exercises and their sets in one database call
  // LEFT JOIN ensures exercises with no sets yet are still included
  // aliases (AS exercise_id etc) prevent column name collisions between tables
  const rowsResult = await pool.query(`
    SELECT
      exercises.id AS exercise_id,
      exercises.name AS exercise_name,
      exercises.muscle_group,
      sets.id AS set_id,
      sets.reps,
      sets.weight,
      sets.set_number
    FROM exercises
    LEFT JOIN sets ON sets.exercise_id = exercises.id
    WHERE exercises.workout_id = $1
    ORDER BY exercises.id, sets.set_number
  `, [id])

  // passing .rows to the helper
  const exercises = groupExercisesWithSets(rowsResult.rows)

  // spread workout's own properties and add exercises array
  // result shape: { id, name, date, user_id, exercises: [{ id, name, sets: [] }] }
  res.json({ ...workout, exercises })
})

// GET /api/workouts/progress/:exerciseName
// returns max weight per session for a specific exercise name
router.get('/progress/:exerciseName', requireAuth, async(req, res) => {
  // exerciseName comes from the URL — e.g. /progress/Bench%20Press
  const { exerciseName } = req.params

  // this query climbs the chain: sets → exercises → workouts
  const result = await pool.query(`
    SELECT
      workouts.date,
      MAX(sets.weight) AS maxweight
    FROM sets
    JOIN exercises ON sets.exercise_id = exercises.id
    JOIN workouts ON exercises.workout_id = workouts.id
    WHERE exercises.name = $1
    AND workouts.user_id = $2
    GROUP BY workouts.date
    ORDER BY workouts.date ASC
  `, [ exerciseName, req.userId])
     // needs to be in order (exercises first then userid)

  res.json(result.rows)
})

router.delete('/:id', requireAuth, async(req, res) => {
  const { id } = req.params

  // verify if the workout is there
  const workoutResult = await pool.query('SELECT * FROM workouts WHERE id = $1', [id])
  const workout = workoutResult.rows[0]

  if (!workout) return res.status(404).json({ error: 'Workout not found' })
  if (workout.user_id !== req.userId) return res.status(403).json({ error: 'Forbidden' })

  // must delete bottom-up: sets first, then exercises, then the workout
  // each layer has a foreign key pointing up — delete children before parents
  await pool.query(`
    DELETE FROM prs
    WHERE set_id IN (
      SELECT sets.id
      FROM sets
      JOIN exercises ON sets.exercise_id = exercises.id
      WHERE exercises.workout_id = $1
    )
  `, [id])

  // then the existing deletes, in order
  await pool.query(`
    DELETE FROM sets
    WHERE exercise_id IN (SELECT id FROM exercises WHERE workout_id = $1)
  `, [id])

  await pool.query('DELETE FROM exercises WHERE workout_id = $1', [id])
  await pool.query('DELETE FROM workouts WHERE id = $1', [id])

  res.json({ message: 'Workout deleted' })
})

module.exports = router
```

```javascript
// fill is computed here (not a CSS class) because alpha is a continuous
// value driven by data — a static class can't express "0.37 trained" vs "0.82 trained".
// shared by MuscleBodyChart (the SVG regions) and MuscleChart (the legend swatches)
// so both always agree on what a given intensity looks like.
export function getFill(group, intensityByGroup) {
  const intensity = intensityByGroup?.[group] ?? 0;
  if (!intensity) return "var(--border)";
  const alpha = 0.15 + intensity * 0.85;
  return `rgba(233, 69, 96, ${alpha})`;
}
```

```javascript
// reads VITE_API_URL in production; falls back to '/api' for local dev (Vite proxy)
const BASE_URL = import.meta.env.VITE_API_URL || '/api'

// helper — builds the Authorization header from the token
// called inside every function that hits a protected route
// this is why we don't need to pass token as a param every time —
// the caller passes it once and this function formats it correctly
function authHeaders(token) {
  return {
    'Authorization': `Bearer ${token}`,
    'Content-Type': 'application/json'
  }
}

// central handler for every API response
// if the token is dead (401), clear the session and bounce to login
async function handleResponse(response, errorMessage) {
  // server rejects the token (expired or invalid)
  if (response.status === 401) {
    // if passes, remove token and username
    localStorage.removeItem("token")
    localStorage.removeItem("username")

    // redirect to login page
    window.location.href = '/login'
    throw new Error("Session expired, please log in again.")
  }

  // any other failure
  if (!response.ok) {
    throw new Error(errorMessage)
  }

  return response.json()
}

// GET /api/workouts — fetch all workouts for the logged-in user
export async function getWorkouts(token) {
  const response = await fetch(`${BASE_URL}/workouts`, {
    // GET requests don't have a body but still need the auth header
    // the server uses the token to know WHOSE workouts to return
```

```jsx
    <svg viewBox="0 0 200 340" width="100%" height="100%" role="img" aria-label={`Muscle training volume, ${view} view`}>
      {SILHOUETTE.map((s, i) =>
        s.shape === "circle" ? (
          <circle key={i} cx={s.cx} cy={s.cy} r={s.r} fill="var(--bg-card)" stroke="var(--border)" />
        ) : (
          <rect
            key={i}
            x={s.x}
            y={s.y}
            width={s.width}
            height={s.height}
            rx={s.rx}
            fill="var(--bg-card)"
            stroke="var(--border)"
          />
        )
      )}

      {regions.map((r, i) =>
        r.shape === "ellipse" ? (
          <ellipse
            key={i}
            data-muscle-group={r.group}
            cx={r.cx}
            cy={r.cy}
            rx={r.rx}
            ry={r.ry}
            style={{ fill: getFill(r.group, intensityByGroup) }}
          />
        ) : (
          <rect
            key={i}
            data-muscle-group={r.group}
            x={r.x}
            y={r.y}
            width={r.width}
            height={r.height}
            rx={r.rx}
            style={{ fill: getFill(r.group, intensityByGroup) }}
          />
        )
      )}
    </svg>
  );
```

WHY: The page at /muscles. Fetches muscle-volume data on mount
(same pattern as Dashboard.jsx). Computes `tonnageByGroup` (a
lookup) and `intensityByGroup` (each group's tonnage divided by
whichever group has the MOST tonnage, so the highest-volume group
is always rendered at full intensity — see risk item F in section 5
for the implication of this). Shows an explicit empty-state message
if there's no tagged/logged data yet, a front/back toggle, and a
legend with each group's raw tonnage number next to a swatch that
matches its rendered color.

FULL FILE:
```jsx
import { useEffect, useState } from "react";
import { useAuth } from "../context/AuthContext";
import { getMuscleVolume } from "../api/workouts";
import { MuscleBodyChart } from "../components/MuscleBodyChart";
import { getFill } from "../utils/muscleFill";
import { MUSCLE_GROUPS } from "../constants/muscleGroups";
import styles from "../styles/MuscleChart.module.css";

export function MuscleChart() {
  const [view, setView] = useState("front");
  const [volume, setVolume] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  const { token } = useAuth();

  useEffect(() => {
    async function fetchVolume() {
      try {
        setLoading(true);
        const data = await getMuscleVolume(token);
        setVolume(data);
      } catch (err) {
        setError(err.message);
      } finally {
        setLoading(false);
      }
    }

    fetchVolume();
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, []);

  if (loading) return <div>Loading...</div>;
  if (error) return <div>Error: {error}</div>;

  // volume is [{ muscle_group, tonnage }] for groups with logged data — turn it
  // into a lookup, then scale every group 0..1 relative to whichever is highest
  const tonnageByGroup = {};
  for (const row of volume) {
    tonnageByGroup[row.muscle_group] = Number(row.tonnage);
  }

  const maxTonnage = Math.max(0, ...Object.values(tonnageByGroup));

  const intensityByGroup = {};
  for (const group of MUSCLE_GROUPS) {
    intensityByGroup[group.value] = maxTonnage > 0
      ? (tonnageByGroup[group.value] ?? 0) / maxTonnage
      : 0;
  }

  return (
    <div className={styles.container}>
      <h1>Muscle Chart</h1>

      {volume.length === 0 && (
        <p className={styles.empty}>
          No tagged training data yet — tag an exercise with a muscle group
          and log a set to see it here.
        </p>
      )}

      <div className={styles.toggleRow}>
        <button
          className={`${styles.toggleBtn} ${view === "front" ? styles.toggleBtnActive : ""}`}
          onClick={() => setView("front")}
        >
          Front
        </button>
        <button
          className={`${styles.toggleBtn} ${view === "back" ? styles.toggleBtnActive : ""}`}
          onClick={() => setView("back")}
        >
          Back
        </button>
      </div>

      <div className={styles.layout}>
        <div className={styles.chartWrap}>
          <MuscleBodyChart view={view} intensityByGroup={intensityByGroup} />
        </div>

        <div className={styles.legend}>
          {MUSCLE_GROUPS.map((group) => (
            <div key={group.value} className={styles.legendRow}>
              <span className={styles.legendName}>
                <span
                  className={styles.legendSwatch}
                  style={{ background: getFill(group.value, intensityByGroup) }}
                />
                {group.label}
              </span>
              <span className={styles.legendTonnage}>
                {tonnageByGroup[group.value]
                  ? `${tonnageByGroup[group.value].toLocaleString()} lbs`
                  : "—"}
              </span>
            </div>
          ))}
        </div>
      </div>
    </div>
  );
}
```

5. FINDINGS — RISKS / POSSIBLE FUTURE ERRORS IF NOT HANDLED WELL
------------------------------------------------------------------

A. NO MIGRATION FRAMEWORK — MANUAL DB SYNC RISK
   Every future schema change requires (1) hand-editing setup-db.js
   and (2) manually running `node setup-db.js` against the live
   Neon DB. If step 2 is ever skipped after a future schema edit,
   the deployed app will throw Postgres "column does not exist"
   errors on the very next request that touches that column. This
   risk grows as Part 5 (analytics) will likely need more schema
   changes.

B. LEGACY EXERCISES HAVE muscle_group = NULL
   The /muscle-volume query filters `WHERE muscle_group IS NOT
   NULL`, so any exercise logged before this update simply won't
   contribute to the chart — correct/safe behavior, but may look
   like "missing" data to you if you remember training something
   the chart doesn't reflect. There's no bulk re-tagging tool built;
   old exercises would need to be re-tagged manually if you want
   them reflected (not currently possible — there's no edit-exercise
   UI, only add/delete).

C. DUPLICATED MUSCLE_GROUPS LIST (frontend + backend)
   If you ever add/rename/remove a muscle group, BOTH
   server/constants/muscleGroups.js AND src/constants/muscleGroups.js
   must be updated together. If they drift out of sync:
     - Frontend offers a group the backend doesn't recognize →
       exercise creation fails with a 400 "Invalid muscle_group"
       error.
     - Backend accepts a group the frontend doesn't know how to
       label/render → it would show up as an unlabeled/blank legend
       row or an uncolored, unlabeled chart region.

D. CASE-SENSITIVE EXACT-MATCH VALIDATION ON THE BACKEND
   `MUSCLE_GROUPS.includes(muscle_group)` requires an exact
   lowercase match. This is fine as long as ALL exercise creation
   goes through this app's own dropdown (which always sends the
   correct lowercase value). But if the API is ever called directly
   (Postman, curl, a future mobile client, etc.) with a differently
   -cased value like "Chest" instead of "chest", it will be rejected
   with a 400 even though it's conceptually a valid value. No
   `.toLowerCase()` normalization was added. Worth adding if this
   API is ever consumed by more than this one frontend.

E. ALL-TIME TONNAGE, NO TIME DECAY (deliberate v1 scope, but a
   real limitation until Part 5)
   The chart's "intensity" is a LIFETIME total. A muscle group
   trained heavily months ago but not touched recently will still
   show as fully lit today — nothing distinguishes "trained a lot
   ever" from "trained a lot recently." If you expect the chart to
   reflect your CURRENT training focus, this will look wrong until
   a time-windowed version of the query is built (natural fit for
   Part 5's analytics work — one extra `AND workouts.date >= ...`
   clause).

F. RELATIVE (NOT ABSOLUTE) INTENSITY SCALING
   Each group's intensity = its tonnage ÷ whichever single group has
   the MOST tonnage. That means the highest-volume group is ALWAYS
   rendered at full saturation — even if, in absolute terms, it's
   barely any volume (e.g. a brand-new account with just one logged
   set will show that one muscle group as "maximally trained," which
   overstates reality). This is a relative visualization by design,
   but could be misleading without a caption. Worth a tooltip or
   note clarifying "relative to your own history" if this comes up
   as confusing later.

G. SVG REGION COORDINATES ARE HAND-ESTIMATED, NOT VISUALLY TESTED
   The rectangles/ellipses in MuscleBodyChart.jsx were placed by
   reasoning about a 200x340 coordinate grid, not by rendering and
   eyeballing in an actual browser (this session only ran `eslint`
   and `vitest`, not a visual check — the schema migration hasn't
   even been applied yet, so the page can't fully function against
   live data anyway). Regions may overlap oddly or sit off from the
   silhouette. Expect to nudge x/y/width/height/rx values after
   actually looking at /muscles in a browser.

H. UNVERIFIED AGAINST REAL DATABASE RESPONSES
   `Number(row.tonnage)` assumes Postgres's SUM() over a REAL column
   comes back as something Number() parses cleanly via the `pg`
   driver. This is a standard, low-risk assumption, but it has NOT
   been exercised against the live database yet, because the schema
   migration (setup-db.js) has not been run. Worth a quick sanity
   check the first time you load /muscles with real data.

I. NO DRILL-DOWN INTERACTIVITY (deliberately out of scope)
   You can't click "quads" to see which exercises contributed to
   that number. This mirrors the still-unbuilt Part 2 "clickable
   PR" feature, but for muscle regions — not built here, flagged as
   a natural future enhancement, not a bug.

J. ExerciseChart.jsx REMAINS DISABLED
   The existing commented-out `<ExerciseChart>` line in
   WorkoutDetail.jsx was left untouched — still disabled, not
   related to this work, not reactivated.

K. PRE-EXISTING LINT ERROR IN AuthContext.jsx (NOT introduced this
   session — confirmed via `git diff` showing zero changes to that
   file)
   ESLint's `react-hooks/set-state-in-effect` rule flags
   AuthContext.jsx calling setToken/setUser synchronously inside a
   useEffect that restores the session from localStorage on mount.
   This is a recognized React anti-pattern (can trigger cascading
   renders) but pre-dates this session and is out of scope for
   Part 3/4. Worth fixing at some point.

L. WHY getFill LIVES IN ITS OWN FILE (src/utils/muscleFill.js)
   Originally the fill-color function was defined directly inside
   MuscleBodyChart.jsx and exported alongside the component. ESLint's
   `react-refresh/only-export-components` rule flagged this — Vite's
   Fast Refresh (hot reload) only works reliably when a component
   file exports ONLY components, not a mix of a component and a
   plain function. Moving getFill into its own utils file both fixed
   the lint error and gave MuscleChart.jsx (the legend) and
   MuscleBodyChart.jsx (the SVG) one shared source of truth for the
   color formula, so they can never visually disagree.
